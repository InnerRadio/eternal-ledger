PURPAWS
SERVER-ISSUED JOURNEY REFERENCE AUTHORITY v1

STATUS
DEFINED
VERIFIED
NOT YET LOCKED


======================================================================
1. PURPOSE
======================================================================

This contract selects the concrete continuity representation required
by the locked Attribution Context Duplicate / Replay Semantics.

The system requires a way to distinguish:

    many people using one reusable share link

from:

    many requests belonging to one person's continuing journey

This authority defines that mechanism.

It does NOT implement it.


======================================================================
2. GOVERNING DESIGN
======================================================================

PurPaws will use a SERVER-ISSUED OPAQUE JOURNEY REFERENCE.

The reference will be:

    generated by PurPaws
    cryptographically strong
    unpredictable
    meaningless to the client
    unrelated to participant identity
    unrelated to referrer identity
    unrelated to reward value

The client may carry the reference.

The client does not create its authority.


======================================================================
3. REFERENCE GENERATION
======================================================================

The raw journey reference must be generated from a cryptographically
secure random source.

Implementation target:

    Python secrets module

Conceptual generation:

    secrets.token_urlsafe(32)

This provides approximately 256 bits of random source material before
URL-safe encoding.

The reference MUST NOT be generated from:

    campaign_id
    affiliate_id
    referral_code
    user_id
    email
    IP address
    user agent
    timestamp
    sequential database ID
    predictable counter


======================================================================
4. VERSIONED EXTERNAL FORM
======================================================================

The externally carried reference SHOULD use a small version prefix.

Conceptual form:

    ppj1_<opaque-random-value>

The prefix identifies token format/version only.

It contains no participant identity.

It contains no Campaign identity.

It contains no referrer identity.

It contains no economic information.


======================================================================
5. SERVER STORES HASH — NOT RAW REFERENCE
======================================================================

PurPaws must not persist the raw browser-carried journey reference as
canonical database state.

The server stores a one-way digest.

Conceptual persisted field:

    journey_reference_hash

Canonical digest:

    SHA-256(raw journey reference)

Expected textual representation:

    64 lowercase hexadecimal characters

Therefore:

    browser carries raw reference
        ↓
    server hashes presented reference
        ↓
    database lookup by hash
        ↓
    Attribution Context resolved

A database leak should not automatically expose active browser-carried
journey references.


======================================================================
6. UNIQUE SERVER-SIDE CONTINUITY KEY
======================================================================

journey_reference_hash must uniquely identify the active canonical
journey reference.

The persistence layer must eventually enforce uniqueness.

This is the atomic duplicate boundary for the SAME journey reference.

It is NOT global uniqueness for:

    Campaign
    Affiliate
    referral code
    participant
    share URL


======================================================================
7. ATTRIBUTION CONTEXT RELATIONSHIP
======================================================================

One active journey reference resolves to one Attribution Context.

Conceptually:

    raw journey reference
        ↓
    SHA-256
        ↓
    journey_reference_hash
        ↓
    AttributionContext

The Attribution Context remains canonical provenance.

The raw journey reference is only a continuity credential.


======================================================================
8. JOURNEY REFERENCE IS NOT AUTHENTICATION
======================================================================

Possession of a journey reference MUST NOT establish:

    logged-in identity
    participant_user_id
    Affiliate identity
    Campaign Enrollment
    Conversion
    Reward
    Commission
    Token entitlement
    Settlement authority

Journey reference means only:

    "continue the server-recognized attribution journey associated
     with this reference"

Nothing more.


======================================================================
9. JOURNEY REFERENCE IS A BEARER CONTINUITY SECRET
======================================================================

The raw journey reference is bearer material.

Anyone possessing it may attempt to continue the anonymous attribution
journey.

Therefore it must be treated as sensitive.

It must not be:

    logged unnecessarily
    exposed in analytics payloads
    placed in public HTML
    returned in public directory records
    embedded in reusable referral links
    included in Referer-leaking URLs


======================================================================
10. DO NOT PUT JOURNEY REFERENCE IN SHARE URL
======================================================================

Reusable Campaign / referral links identify provenance transport.

They must NOT contain the per-journey server-issued reference.

Example reusable link may carry sufficient referral hints to begin
validation.

Then:

    first validated arrival
        ↓
    PurPaws creates unique journey reference for that arrival

This ensures:

    one shared URL
        ↓
    many independent people
        ↓
    many independent server-issued journeys


======================================================================
11. BROWSER TRANSPORT
======================================================================

The default browser continuity transport is:

    Secure cookie
    HttpOnly cookie
    SameSite=Lax
    Path=/

The cookie SHOULD be host-only unless future deployment architecture
requires a broader domain scope.

The browser cookie carries the RAW opaque journey reference.

JavaScript should not require access to it.

Therefore HttpOnly is required for the normal browser mechanism.


======================================================================
12. HTTPS REQUIREMENT
======================================================================

Journey reference cookies must be Secure.

Production journey continuity therefore requires HTTPS.

The reference must not intentionally travel over plaintext HTTP.


======================================================================
13. SAME-SITE POLICY
======================================================================

SameSite=Lax is the default authority choice.

Reason:

It supports ordinary top-level navigation continuity while reducing
cross-site request exposure compared with SameSite=None.

A future requirement to weaken SameSite policy must be separately
justified and reviewed.


======================================================================
14. COOKIE NAME
======================================================================

Conceptual cookie name:

    pp_journey

The cookie name itself carries no authority.

If implementation inspection reveals a naming conflict, the name may
change without changing this authority contract.

The security semantics are authoritative, not the cosmetic name.


======================================================================
15. EXPIRY
======================================================================

A journey reference MUST have bounded validity.

Its browser expiry must not outlive the corresponding canonical
Attribution Context authority.

AttributionContext.expires_at is the canonical lifecycle boundary.

Exact attribution-window duration is NOT selected by this contract.

It must be defined separately as Campaign / Attribution Policy.

Therefore:

    bounded expiry = REQUIRED

    exact number of days = NOT YET LOCKED


======================================================================
16. VALIDATION
======================================================================

A presented journey reference must be validated before use.

Validation requires:

    expected format/version
    cryptographically sufficient raw value
    SHA-256 lookup
    exactly one matching Attribution Context
    acceptable context status
    context not expired
    provenance compatibility
    participant-binding compatibility where participant resolved

Failure must fail safely.


======================================================================
17. UNKNOWN REFERENCE
======================================================================

If a presented reference hashes to no known Attribution Context:

    do not invent continuity
    do not bind it to arbitrary provenance
    do not create participant identity from it

The request may be evaluated as a potential NEW JOURNEY using normal
Creation Authority rules.


======================================================================
18. MALFORMED REFERENCE
======================================================================

Malformed journey references are not trusted.

They must not trigger:

    database identity assignment
    participant resolution
    Campaign Participation
    Conversion
    Reward
    settlement

Malformed reference handling must fail safely.


======================================================================
19. NEW JOURNEY FLOW
======================================================================

Conceptual flow:

    inbound reusable Campaign/referral route
        ↓
    validate Campaign
        ↓
    validate referrer where applicable
        ↓
    establish sufficient provenance
        ↓
    generate new opaque journey reference
        ↓
    hash reference
        ↓
    create Attribution Context with unique reference hash
        ↓
    set secure HttpOnly journey cookie

The browser receives continuity.

The server retains canonical provenance.


======================================================================
20. CONTINUING JOURNEY FLOW
======================================================================

Conceptual flow:

    request carries pp_journey
        ↓
    validate format
        ↓
    SHA-256(raw reference)
        ↓
    resolve Attribution Context
        ↓
    validate status / expiry
        ↓
    validate compatible provenance
        ↓
    continue SAME Attribution Context

No duplicate canonical context is created merely because the request
was repeated.


======================================================================
21. CONFLICTING PROVENANCE
======================================================================

If an existing journey resolves to:

    Campaign X
    Referrer A

and a later request presents claims for:

    Campaign X
    Referrer Z

or:

    Campaign Y

the existing context must not be silently rewritten.

The system must classify the request as conflicting provenance or a
potentially distinct new journey according to later Creation Authority
rules.

Historical origin is not last-write-wins.


======================================================================
22. ANONYMOUS → MEMBER RESOLUTION
======================================================================

Anonymous journey:

    participant_user_id = NULL

After successful PurPaws registration or authentication:

    participant identity comes from account/authentication authority

not:

    browser-submitted participant_user_id

If compatible, the existing Attribution Context may then resolve to
that authenticated member.


======================================================================
23. ROTATION ON PARTICIPANT BINDING
======================================================================

When an anonymous Attribution Context becomes bound to an authenticated
participant, the journey reference SHOULD be rotated.

Conceptual operation:

    old anonymous raw reference
        ↓
    authenticate / register B
        ↓
    bind participant = B
        ↓
    generate NEW opaque reference
        ↓
    replace stored journey_reference_hash
        ↓
    set replacement Secure HttpOnly cookie

The prior anonymous reference is no longer active.

This reduces fixation / pre-binding reference reuse risk.


======================================================================
24. ROTATION PRESERVES CONTEXT
======================================================================

Reference rotation MUST NOT create a new Attribution Context.

It changes the continuity credential.

It does not change:

    original Campaign
    original referrer
    original evidence
    created_at
    canonical Attribution Context identity

Conceptually:

    AC1 + Reference R1
        ↓ participant binds
    AC1 + Reference R2

not:

    AC1
        ↓
    AC2


======================================================================
25. RESOLVED PARTICIPANT CONFLICT
======================================================================

If a journey is already resolved to participant B and the same
reference is later presented while authenticated as participant C:

    DO NOT rebind B → C

The request must fail safely or be classified as conflicting.

Participant identity is not bearer-token transferable.


======================================================================
26. LOGOUT DOES NOT ERASE PROVENANCE
======================================================================

Logging out may affect authentication.

It does not erase Attribution Context historical provenance.

Journey continuity behavior after logout may be governed by later
product policy.

The system must not rewrite origin because authentication state changed.


======================================================================
27. COOKIE LOSS
======================================================================

A user may:

    clear cookies
    change browser
    use private browsing
    change device

PurPaws must accept that continuity may be lost.

The system MUST NOT compensate by invasive device fingerprinting.

If continuity cannot be safely proven, a later arrival may become a
new journey.


======================================================================
28. CROSS-DEVICE CONTINUITY
======================================================================

Anonymous cross-device continuity is NOT automatically guaranteed.

A server-issued cookie-based journey reference is naturally local to
the browser carrying it.

Once a participant becomes an authenticated member, later authorities
may use authenticated identity for participant continuity.

This contract does not create anonymous cross-device fingerprinting.


======================================================================
29. CONCURRENCY
======================================================================

The unique persisted journey_reference_hash is the intended atomic
continuity boundary.

Future implementation must enforce uniqueness at the database layer.

If two workers attempt to create the same canonical reference hash,
only one may succeed.

Random collision probability should be negligible.

Application logic must still handle uniqueness failure safely.


======================================================================
30. RANDOM COLLISION
======================================================================

Cryptographically random 256-bit source material makes accidental
collision operationally negligible.

However, database uniqueness remains required.

Security design must not rely solely on probability when an inexpensive
integrity constraint is available.


======================================================================
31. HASH LOOKUP
======================================================================

The raw reference should be hashed before database lookup.

The server does not need to decrypt or recover the stored value.

Therefore journey continuity uses:

    equality by secure digest

not:

    reversible encryption of the reference


======================================================================
32. HASH ALGORITHM
======================================================================

v1 canonical digest:

    SHA-256

This hash is being used as a lookup digest over a high-entropy random
secret, not as a password hashing mechanism.

Password hashing functions are therefore not required for this purpose.

If the reference-generation entropy is weakened in any future design,
this assumption must be revisited.


======================================================================
33. NO ECONOMIC CONTENT IN REFERENCE
======================================================================

The journey reference must encode no client-readable economic claim.

It must not contain:

    payout amount
    payout type
    reward amount
    commission amount
    token amount
    discount value
    settlement status

Economic authority remains downstream.


======================================================================
34. NO IDENTITY CONTENT IN REFERENCE
======================================================================

The journey reference must encode no client-readable identity claim.

It must not expose:

    participant_user_id
    participant email
    referring_user_id
    referrer email
    organization membership

It is opaque continuity material.


======================================================================
35. NO CAMPAIGN / REFERRER CONTENT REQUIRED
======================================================================

The raw journey reference need not encode:

    campaign_id
    affiliate_id
    referral_code

Those values already live as canonical server-side Attribution Context
provenance.

The reference locates authority.

It does not duplicate authority.


======================================================================
36. SHARE LINK VS JOURNEY REFERENCE
======================================================================

SHARE LINK

Purpose:
    reusable provenance transport

Cardinality:
    one link may serve many people

May contain:
    campaign/referral hints subject to server validation


JOURNEY REFERENCE

Purpose:
    individual journey continuity

Cardinality:
    one active reference resolves one canonical Attribution Context

Must be:
    server issued
    opaque
    unpredictable
    sensitive


======================================================================
37. REFERENCE != CONTEXT ID
======================================================================

The externally carried journey reference MUST NOT simply be the
integer AttributionContext.id.

Sequential database IDs are predictable.

Therefore:

    AttributionContext.id != external journey reference

The internal numeric primary key remains internal authority identity.


======================================================================
38. REFERENCE != CLICK ID
======================================================================

The journey reference MUST NOT be AffiliateClick.id.

Click ID identifies an interaction event.

Journey reference identifies continuity.

These remain separate.


======================================================================
39. REFERENCE != AFFILIATE ID
======================================================================

The journey reference MUST NOT be Affiliate ID.

Affiliate ID identifies a participant/referrer identity dimension.

Journey reference identifies a particular continuity path.


======================================================================
40. REFERENCE != REFERRAL CODE
======================================================================

The journey reference MUST NOT be referral code.

Referral codes are reusable provenance identifiers.

Journey references distinguish individual journeys using them.


======================================================================
41. SCHEMA CONSEQUENCE
======================================================================

The existing AttributionContext model/table does not yet contain the
required persisted journey_reference_hash.

Therefore implementation will require an explicit schema evolution
before Creation Authority can use this mechanism.

Expected semantic field:

    journey_reference_hash
        String
        non-null for journey-enabled contexts
        unique
        indexed

The exact SQLite migration procedure is NOT performed by this contract.

It must follow:

    Observe
    Inspect
    Understand
    Define
    Verify
    Lock
    Continue


======================================================================
42. EXISTING EMPTY TABLE ADVANTAGE
======================================================================

Attribution Context currently exists as a first-class table with no
created attribution rows.

This provides a safer migration window.

Nevertheless, schema evolution must still be deliberate and verified.

No destructive recreation is authorized by this contract.


======================================================================
43. COOKIE IS NOT DATABASE AUTHORITY
======================================================================

The cookie carries a reference.

The database remains canonical.

Deleting or modifying a cookie does not rewrite database provenance.

Presenting an arbitrary cookie value does not create authority.


======================================================================
44. TOKEN THEFT BOUNDARY
======================================================================

A stolen anonymous journey reference may permit attempted continuation
of that anonymous context.

It MUST NOT permit:

    authentication
    account takeover
    payout
    participant rebinding
    reward settlement

Rotation upon participant binding limits continued use of the original
anonymous reference.


======================================================================
45. REGISTRATION CONTINUITY
======================================================================

Desired flow:

    Member A shares Campaign X
        ↓
    Person B follows reusable link
        ↓
    server validates A + X
        ↓
    creates AC1
        ↓
    generates R1
        ↓
    stores SHA-256(R1)
        ↓
    sets secure HttpOnly cookie R1
        ↓
    B browses / revisits
        ↓
    R1 continues AC1
        ↓
    B registers
        ↓
    authentication authority identifies B
        ↓
    AC1 participant resolves to B
        ↓
    rotate R1 → R2
        ↓
    same AC1 continues
        ↓
    B joins Campaign X
        ↓
    enrollment resolves

No Campaign rediscovery required.

No referrer overwrite.

No participant identity confusion.


======================================================================
46. FAILURE MODES
======================================================================

UNKNOWN REFERENCE

    no matching hash
    → no assumed continuity


EXPIRED REFERENCE

    context expired
    → no current continuity authority


MALFORMED REFERENCE

    invalid format
    → reject as continuity reference


CONFLICTING PARTICIPANT

    context bound to B, authenticated user C
    → do not rebind


CONFLICTING PROVENANCE

    existing context origin disagrees with incoming claim
    → do not overwrite


DUPLICATE CONCURRENT CREATE

    uniqueness conflict
    → resolve safely / do not manufacture duplicate contexts

51. FINAL AUTHORITY STATEMENT
======================================================================

The reusable referral link identifies provenance transport.

PurPaws creates the individual journey identity.

That identity is an opaque cryptographically random server-issued
reference.

The browser may carry the raw reference in a secure HttpOnly cookie.

The server stores only its SHA-256 digest.

The reference resolves continuity.

The Attribution Context remains canonical provenance.

Authentication remains participant identity authority.

Campaign Participation remains Enrollment authority.

Reward Policy remains economic authority.

Settlement remains settlement authority.

No layer impersonates another.
